# #7: 全画面と発表者ウィンドウ

## 結論

Ruby のキーボード／クリック処理から Fullscreen API・window.open・postMessage を利用できた。
別ウィンドウに現在の本文とノートを表示し、メインのページ移動に同期できた。

## 検証

- ユーザーイベント内で待機を挟まず requestFullscreen / window.open を実行。
- ボタン・F による全画面、終了ボタン・Ruby の Esc 処理による解除を実際の fullscreenElement で確認。
- N で発表者ウィンドウを開き、ノートの基本書式と本文・ページ番号を照合。
- origin と source を照合した postMessage のみ受け取り、発表者ウィンドウ自身からの偽メッセージを無視。
- ウィンドウを閉じた後もメインのページ移動が動作する。
- Permissions Policy `fullscreen=()` と CSP sandbox による実際の拒否で、通知が表示されることを確認。

## 制約

headless Chrome はユーザー操作なしの起動を許可する場合があった。
そのため「ユーザー操作なしなら必ず拒否される」ことは自動テストで主張せず、
失敗経路はブラウザーのポリシー制限で確認する。通常ブラウザーの実設定は README の手動手順で確認する。

発表者画面のイベントはメイン側の同じ Ruby VM が登録する。別ウィンドウごとの wasm 起動は不要。
同期はメイン→発表者の一方向で、メインの終了・再読込後の復旧は今回の範囲外。
